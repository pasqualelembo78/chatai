2. BUG BLOCCANTI
================================================================================

[CRITICO] BUG #1 — Risposte AI silenziose (fallback loop)
  File: ai_engine.py (funzione _ollama_generate)
  Sintomo: Se un provider AI non risponde o dà errore, l'app mostra
  sempre il testo statico "Raccontami di piu.'" senza notificare l'utente.
  Causa: Le eccezioni vengono ingoiate silenziosamente, il fallback
  non propaga errori al client. L'utente non capisce se il server è
  giù, il modello non è installato, o la chiave API è scaduta.
  Impatto: L'APP È ESSENZIALMENTE ROTTA se l'AI non è raggiungibile.

[CRITICO] BUG #2 — UI rotta su Android 15 (edge-to-edge)
  File: layout XML (activity_main, fragment_main)
  Sintomo: La barra di navigazione di sistema (indietro/home/recenti)
  si sovrappone al campo di input messaggi, rendendolo inaccessibile.
  Causa: targetSdk 35 forza edge-to-edge rendering. Nessun
  fitsSystemWindows o setOnApplyWindowInsetsListener implementato.
  Impatto: L'APP È INUTILIZZABILE SU ANDROID 15.

4. CODICE E ARCHITETTURA
================================================================================

[ALTO] MainFragment.java ~1912 righe
  - Gestisce: socket events, streaming AI, UI chat, recording audio,
    image picking, settings dialog, TTS, riconnessione, e altro.
  - Violazione palese del Single Responsibility Principle.
  - Da spezzare in: ChatViewModel, AudioManager, ImageManager,
    SocketManager, ConnectionManager.

[ALTO] HttpURLConnection duplicato in 5+ file
  - HomeFragment, ChatListFragment, CreateFragment,
    CharacterDetailActivity, ecc. hanno copie identiche di
    httpGet()/httpPost().
  - No connection pooling, no retry automatico, no interceptors.
  - Da sostituire con OkHttp/Retrofit o almeno un utility class.

[ALTO] Nessuna dependency injection
  - Singleton acceduti via ((ChatApplication) getApplication()).
  - Da migrare a Hilt o manual DI.

[MEDIO] Threading manuale raw
  - new Thread(() -> ...) ed ExecutorService ovunque.
  - No coroutines, no RxJava, no Lifecycle-aware threading.
  - Le fragment possono leakare se distrutte mentre i thread girano.

[MEDIO] Assenza type hints nel backend Python
  - server.py, storage.py, emotion_engine.py ecc. non hanno
    annotazioni di tipo.

[MEDIO] server.py ~1414 righe
  - Tutti i route REST sono nello stesso file. Da modularizzare.

[MEDIO] characters.py contiene dati in codice
  - Le definizioni dei personaggi sono Python dict nel codice.
  - Andrebbero spostate in un file JSON/YAML caricato dinamicamente.

[BASSO] proguard-rules.pro vuoto
  - R8 è abilitato ma senza regole personalizzate.
  - Le classi usate via reflection (Socket.IO?) potrebbero essere rimosse.

[BASSO] SQLite con query non sempre parametrizzate
  - Backend usa parameterized queries (buono).
  - Android (LocalDatabaseHelper) ha qualche concatenazione diretta.

7. INFRASTRUTTURA E DEPLOY
================================================================================

[ALTO] Nessun Container/Docker
  - build_app.sh è l'unico modo per deployare.
  - Ambiente non riproducibile, rischio di environment drift.
  - Servono: Dockerfile + docker-compose.yml (backend, redis, db).

[ALTO] Nessun endpoint /health
  - Mancano readiness e liveness probe per orchestrazione.
  - Serve un endpoint che verifichi: DB, Redis, AI provider.

[MEDIO] Nessun API versioning
  - Endpoint: /chat, /config, /characters — senza /api/v1/.
  - Breaking changes richiederebbero update app obbligatorio.

[MEDIO] Nessun database PostgreSQL
  - SQLite va bene per dev, non per produzione con concorrenza.
  - Migrazione a PostgreSQL necessaria.

[MEDIO] Nessun structured logging
  - I log sono testuali, non in JSON.
  - Nessun log aggregation (ELK, Loki, Datadog).

[BASSO] Nessun monitoring/metriche
  - Prometheus + Grafana citati nella roadmap ma non implementati.
  - Non c'è tracciamento di: latenza AI, error rate, utenti attivi.

[BASSO] Nessun analytics
  - Nessun track di: engagement, retention, feature usage.
  - Firebase Analytics / PostHog / Mixpanel assenti.

[BASSO] Nessun crash reporting su Android
  - Firebase Crashlytics / Sentry Android SDK assenti.
  - I crash sono invisibili.

  - Architettura solida con multi-provider AI e failover
